# Платежи: только sandbox

Реальные списания не реализованы и не выполняются. `SANDBOX_PAYMENTS_ENABLED=false` по умолчанию. Нет автоматической покупки платного API или платёжного аккаунта.

## Тестовый flow

1. В тестовой среде задайте `PAYMENT_PROVIDER=sandbox`, `SANDBOX_PAYMENTS_ENABLED=true`, случайный `PAYMENT_WEBHOOK_SECRET` (32+ символов).
2. В `/admin/monetization` включите нужный платный продукт. Цена хранится в копейках в PostgreSQL.
3. Работодатель выбирает продукт и опубликованную вакансию для продвижения или пакет размещений.
4. `make_order` авторизует работодателя, берёт текущую цену из базы и сохраняет снимок продукта. Браузер отправляет только `product_id`, `job_id`, idempotency key.
5. На странице заказа возьмите UUID и выполните на доверенной машине:

```sh
npm run sandbox:pay -- ORDER_UUID
```

Скрипт получает сумму из БД, создаёт подписанное событие и отправляет его на `/api/payments/webhook`. Сервер проверяет HMAC-SHA256, timestamp (±5 минут), структуру события, сумму/валюту из заказа. Только после этого SQL-транзакция меняет статус и активирует права.

```sh
npm run sandbox:pay -- ORDER_UUID --refund
```

Тестовый возврат меняет статус и прекращает продвижение/неизрасходованные права. Повтор одного event_id не создаёт повторных эффектов. Сумма вебхука не может заменить сумму заказа.

## Продукты и политика

NORMAL, BOOST, HIGHLIGHT, VIP, START, BUSINESS, PRO, PRO_EMPLOYER находятся в базе. Примеры цен только в seed; платные продукты выключены. Бесплатная квота и срок задаются в `/admin/settings`. NORMAL является справочным продуктом, не оформляется как платный заказ.

BOOST/VIP применяются только внутри релевантных результатов; коммерческий приоритет идёт после релевантности и свежести. Это намеренно не «показать любую платную вакансию первой». HIGHLIGHT помечает карточку в выдаче поиска.

Пакеты и PRO_EMPLOYER создают ограниченные по времени права размещений с остатком. **Автопродление, платёжные методы, скидки, приоритетная поддержка и бухгалтерские документы не реализованы.** Запись подписки здесь не означает полноценный recurring billing.

## Подключение настоящего провайдера

Реализуйте `PaymentProvider`, проверку подписи именно выбранного провайдера, server-to-server проверку статуса, механизм возвратов, обработку задержанных/неупорядоченных событий и сверку выписок. Измените строгий allowlist `settle_payment`, который сейчас допускает только `sandbox`. Не делайте это простым переименованием строки provider.

Перед реальными продажами нужны решения по кассовым чекам, налогам, оферте, возвратам и условиям платёжного провайдера. Комиссии за реальные платежи не относятся к «бесплатной разработке». Админская монетизация в этой версии честно помечает суммы как тестовые.
