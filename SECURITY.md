# Безопасность и границы проверки

Это описание реализованных механизмов, не сертификат безопасности и не результат проведённого pentest.

## Реализовано

- RLS включён на всех прикладных таблицах. Обычный пользователь не может назначить себе роль, опубликовать вакансию или подтвердить оплату прямой записью в таблицу.
- Клиент Supabase с user JWT для обычных операций; service_role только в backend/worker/scripts.
- `getUser()` проверяет подлинность сессии; серверные страницы и действия админки дополнительно проверяют роль.
- Действия SQL с SECURITY DEFINER имеют фиксированный `search_path`, явный revoke PUBLIC EXECUTE и узкие grant.
- Изменение ролей через админскую транзакцию не позволяет удалить последнего администратора.
- Zod для веб-форм и API; SQL constraints, разрешённые статусы и ownership для прямого PostgREST.
- Server Actions используют защиту Next.js по origin. JSON API избранного/событий/push проверяют origin отдельно.
- Webhook платежей проверяет подпись, время, payload и сумму из БД; Telegram проверяет secret header.
- Rate limiting сохраняется в PostgreSQL и работает между экземплярами. Это не полноценная DDoS-защита; лимиты по email/session не заменяют инфраструктурные лимиты по доверенному IP.
- Тело webhook/JSON ограничено по реально прочитанным байтам. Push endpoints допускают только известные HTTPS-hosts, а не произвольные адреса.
- Неподтверждённая публикация и истёкшие вакансии не доступны в публичном каталоге.
- React экранирует текст, JSON-LD экранирует `<`. Исходный Telegram-текст не вставляется как HTML.
- Файлы: только JPEG/PNG по сигнатуре, до 800 КБ, случайный путь. SVG/HTML не принимаются. EXIF не удаляется автоматически.
- API-ключи не передаются браузеру. Публичный VAPID key является публичным по протоколу, это не приватный ключ.

## До публичного релиза

1. Прогон интеграционных тестов RLS на отдельном Supabase.
2. Аудит всех SECURITY DEFINER функций, бизнес-квот, истории изменений и storage grants.
3. Сверка версии Next.js/React/Supabase с актуальными security advisories, `npm audit`, фиксация lockfile.
4. Настройка CSP под фактическое размещение; в текущем коде есть базовые security headers, но **нет строгой CSP**.
5. Ограничения на уровне CDN/IP, CAPTCHA или другой бесплатный способ защиты массовой регистрации при необходимости.
6. Подтверждённая почта, безопасное восстановление доступа, политика сессий и административных аккаунтов.
7. Проверка резервной копии и реального восстановления, процедура удаления персональных данных и сроков хранения.
8. Утверждённые юридические документы, сведения об операторе, законность переноса Telegram-контактов, локализация ПДн.
9. Полные мобильные и браузерные тесты, доступность, корректность внешних ссылок.
10. Для настоящих платежей отдельный security review, provider verification и сверка возвратов.

Часть служебных административных изменений и записи их журнала выполняется двумя запросами, не одной транзакцией. Модерация, роли и платежи транзакционные. Если требуется строгая неизменяемая аудит-трасса всех admin-операций, перенесите оставшиеся записи в SQL RPC до production.

## Секреты

Не делитесь service_role, паролем PostgreSQL, приватным VAPID, bot token, платёжным webhook secret, Telegram-кодами и сессиями в чате или репозитории. При утечке отзовите/смените ключ у провайдера и обновите все окружения. `.env.example` содержит только названия и безопасные значения по умолчанию.
